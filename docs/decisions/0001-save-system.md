# ADR-0001: セーブ方式

- Status: **Accepted**
- Date: 2026-09-12
- Decider: 主（人間）
- 影響範囲: campaign-dev, engine-dev（マッパー構成）, text-budget（パスワード文字列のPRG消費）

## 文脈

`docs/plan.md` §7 の「最初に主が決めるべき3点」の1つ。**P1 に入る前に確定させたい。**

本作は全12話・三世代にわたるキャンペーンであり、以下の状態を跨いで保持する必要がある:

- ルート分岐1（勢力3択）・分岐2（思想2択）
- 各キャラの生存／死亡（**死亡は永続**）
- 縁値（次世代への継承判定）
- 研究配分（響／錠／灼）
- クリア済み話ID、プール構成

保持すべき情報量の粗い見積もり: フラグ 64〜96 bit ＋ 縁値（16名 × 3〜4 bit）＋
研究配分（3系統 × 5〜6 bit）＋ 進行 8 bit ≒ **20〜30 バイト**。

> 注: 上記「死亡は永続」は本 ADR 起草時点の前提である。ADR-0005（キャラクターの死亡と失敗の扱い）により
> この前提は改められた。保持すべき情報量の見積もり自体は変わらない（生存フラグが
> 「恒久離脱フラグ」に置き換わるだけ）。

## 選択肢

### 案A: バッテリーバックアップ（PRG-RAM $6000-$7FFF + 電池）
- 内容: MMC3 の PRG-RAM を電池でバックアップし、任意の時点でセーブする。
- 利点:
  - 話の途中でも中断できる。プレイ体験が現代的で快適。
  - 保存量の制約が実質なくなる（8KB）。将来の仕様追加に強い。
  - 実装が単純（RAMに書くだけ＋チェックサム）。
- 欠点:
  - **カートリッジのコストが上がる**（電池＋SRAM）。実機頒布を考えるなら無視できない。
  - 電池切れでデータが消える。
  - エミュレータ/フラッシュカートでの挙動差（.sav の扱い）がテストを複雑にする。
- 実装コスト: 小（〜1日）。ただしハード構成が固定される。

### 案B: パスワード継続（世代の変わり目でのみ発行）
- 内容: 世代交代時（S4末／S8末）にパスワードを表示し、そこから再開する。
- 利点:
  - **カートリッジが安い**（電池不要、NROM的な素の構成に近い）。
  - 世代交代という物語上の区切りとパスワードの発行点が一致する。
    「三代記」という構造と、継続点が3つしかないことが噛み合う。
  - セーブデータの改変＝パスワード入力なので、ルート試行のリプレイが手軽になる（周回前提の企画と相性が良い）。
- 欠点:
  - **世代の途中（4話ぶん）で中断できない**。1世代 = 実プレイ 40〜60分を一気にやる前提になる。
  - パスワード生成・検証・入力UIの実装が必要（20〜30バイト → チェックディジット込みで 30〜40 文字級）。
    文字数を減らすには情報の圧縮（縁値の量子化、生存情報のビットパック）が要る。
  - 入力ミスのユーザ体験が悪い。入力画面の作り込みが要る。
- 実装コスト: 中（3〜5日）。圧縮設計＋UI＋検証テスト。

### 案C: 併用（バッテリーがあれば自動セーブ、無ければパスワード）
- 内容: 両方実装し、起動時に PRG-RAM の生死を判定して切り替える。
- 利点: どちらのカートでも動く。
- 欠点: **テスト経路が2倍になる**。代表20経路の回帰が倍増する。得るものに対して高い。
- 実装コスト: 大。推奨しない。

## 決定

**案A（バッテリーバックアップ）を採用する。さらに、シナリオ中途の複数ポイントで
オートセーブを行う。**

主の意図は「現代的なゲーム構成」である。話の区切りだけでなくシナリオの途中からも
再開できることを、本作のプレイ体験の前提として置く。

- 案B を採らない理由: 継続点が世代交代の3箇所に限られ、シナリオ中途の再開ができない。
- 案C を採らない理由: 保存経路が2系統になり、代表20経路の回帰テストが倍増する。

この決定により、**オートセーブポイントは本作の設計要素**になった。
ADR-0005（キャラクターの死亡と失敗の扱い）で定めたシナリオ失敗からの再開は、
このオートセーブポイントを直接の復帰先とする。

## 帰結

### ハードウェア構成（確定）

- iNES ヘッダの **flags6 bit1（バッテリーバックアップ）を立てる**。
- **PRG-RAM $6000-$7FFF（8KB）** をセーブ領域として `cfg/mmc3.cfg` にセグメント定義する。
  MMC3 の PRG-RAM 有効化／書込許可レジスタ（$A001）の制御は engine-dev の責務。
- これらの変更は engine-dev の範囲（`src/header.s`, `cfg/mmc3.cfg`, `src/constants.inc`）である。

### セーブデータの健全性（設計上の必須要件）

- セーブデータには**チェックサム**を持たせる。起動時に検証し、
  **破損していた場合は「セーブデータなし」として扱う**（フォールバック）。
  破損データを部分的に信じて進行させてはならない。
- **オートセーブ中に電源を切られてもデータを壊してはならない。** これは任意ではなく必須要件である。
  実現手段はいずれか:
  - **二面バッファ**: スロットを2面持ち、交互に書き、世代番号＋チェックサムが揃う新しい方を採用する。
  - **書き込み完了フラグ**: 書き込み開始時にフラグを落とし、チェックサム確定後に立てる。
    フラグが落ちたままのスロットは無効とみなす。
  電池切れ・初回起動（PRG-RAM が不定値）も同じ経路で「セーブデータなし」に落ちること。

### オートセーブポイントの定義（データ駆動）

- **オートセーブポイントをどこに置くかはデータで定義する。**
  CLAUDE.md 第1条により、話番号や「ここでセーブ」という判断を `.s` に書いてはならない。
- **`data/scenario.tsv` にオートセーブポイントを表す列を持たせる**想定とする（列の具体形式は
  campaign-dev と stage-author が P3/P4 で確定させる）。シナリオ中途の複数ポイントを表現できること。
- 「シナリオ開始時」も1つのオートセーブポイントとして同じ仕組みで表現する。特別扱いしない。

### 進行への影響

- **ADR-0005 のシナリオ失敗（操作キャラの死亡）→ 直前のオートセーブポイントからの再開は、
  この決定に直接依存する。** オートセーブが無ければ ADR-0005 の失敗時挙動は成立しない。
- **campaign-dev は P4 でセーブを実装してよい。** 本 ADR が Proposed であったことによる
  着手禁止（CLAUDE.md 第6節）は解けた。
- qa-runner: セーブ／ロードを跨ぐ経路が回帰対象に加わる。
  最低限「オートセーブ→リセット→再開で状態が一致する」ことを L2 で検証できる
  （チェックサムと構造の検証はサイクル精度を要さない）。
- text-budget: パスワード入力 UI が不要になったぶん、PRG の見積もりは減る方向。

### 後から覆す場合のコスト

バッテリーを外してパスワードに戻す場合、シナリオ中途の再開が失われるため
ADR-0005 のシナリオ失敗時の復帰仕様を作り直す必要がある。
セーブ実装そのものより、失敗時の体験設計のやり直しが主なコストになる。
