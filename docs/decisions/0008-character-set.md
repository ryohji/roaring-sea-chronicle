# ADR-0008: テキストの文字種と字形

- Status: **Accepted**
- Date: 2026-09-13（決定: 2026-09-14）
- Decider: 主（人間）
- 影響範囲: scenario-writer, text-budget, engine-dev, stage-author, spec-keeper（`data/text/`, `src/text/`, CHR 割当）

## 文脈

会話とシナリオに使う**字そのもの**を用意する必要がある。「ひらがなに限る」としても、
字形（フォント）はそれ自体が相当量を占める。本 ADR は**どの字を持つか**を決めるためのものである。

### 効いてくるのは CHR-ROM の総量ではない

企画書 §7 の CHR 見積もりは 8192 タイル中 約5450 で「余裕あり」としている。
フォント約180タイルは全体の **2.2%** にすぎず、**総量は論点にならない**。

本当の制約は次である。

- **PPU が同時に見える BG パターンテーブルは 256 タイル**（$1000-$1FFF）しかない。
  会話中は、**フォントと背景がこの 256 枚を取り合う**。
- MMC3 の CHR バンクは **1KB 単位（＝64タイル）**で切り替えられる。BG 側は R2〜R5 の **4本**。
  スキャンライン IRQ を使えば画面の途中でも差し替えられる（ステータスバー分割と同じ仕組み）。

つまり「フォントを何字持つか」は **CHR 容量の問題ではなく、会話画面の背景表現力の問題**である。

### 企画書 §7 の「PRG 側の最大リスク: テキスト量」とは別の問題である

**混同しないこと。**

| | 対象 | 効くもの | 担当 |
|---|---|---|---|
| 企画書 §7 のリスク | **PRG** | 台詞の**バイト数**（辞書圧縮で減る） | text-budget / scenario-writer |
| **本 ADR** | **CHR** | 字形の**タイル数**（辞書圧縮では1タイルも減らない） | text-budget / engine-dev |

**両方が同時に効く。** 辞書圧縮をどれだけ効かせてもフォントのタイルは1枚も減らないし、
文字種を絞っても台詞のバイト数は減らない（むしろ言い換えで増えることがある）。

### 実地調査の結果（主が計測済み。この数字を使う）

企画書の固有名詞・シナリオ名から、実際に使われている字を数えた結果:

- **ゲーム内の固有名詞に必要なカタカナ: 29字**
  `ア イ ゥ ウ エ オ ガ ギ ク グ コ サ ザ シ ジ ズ セ ゼ ダ ト ド ナ ハ ミ モ ラ ル ロ ン`
  （ロスター16名＋客将6名＋ゼロ号＋サラズ。**カタカナ46字の全部は要らない**）
  うち濁音9字。濁点を独立タイルにすると 25字。
- **ひらがな: 80字**（清音46＋濁音20＋半濁音5＋小書き9）。台詞に使う以上ほぼ全部要る。
  濁点を独立タイルにすると **57字**（46＋小書き9＋゛＋゜）。
- **シナリオ名・用語の漢字: 67字**
  （波止場の夜／塩堤の崩れ／旧灯台／第一の潮鳴り／商館通り／尾根の砦／巡礼路／沈んだ倉庫区／
  工房／第二の潮鳴り／廃港／沈黙の書庫／稼働炉／海底回廊／潮の芯／都市同盟／山の氏族／
  灯の教団／響／錠／灼／環／機械兵 ほか）
- 数字・記号: 10 ＋ 約15（「」。、！？…ー・空白 など）

> **要確認（spec-keeper）→ 決定節で解消済み（2026-09-14）。** 数字10字は会話画面の
> フォントに含める。以下は起草時の記述であり、記録としてそのまま残す。
>
> 下表の「記号15」列に**数字10字が含まれていない**。
> 数字を表示する（残り時間・縁値・研究配分・話数など）なら各案 **+10タイル／背景 -10タイル**になる。
> 数字を UI 側（ステータスバー）専用として別バンクに置くなら会話画面には効かない。
> **どちらかを主が決めるか、engine-dev の画面設計が固まるまで各案に ±10 の幅があるものとして扱う。**

## 選択肢

> **注（決定後に追記）**: 下表は起草時のものであり、**数字10字を計上していない**。
> 採用された案A の正しい数字は **185タイル／背景71タイル**である（決定節を参照）。
> 表は起草時の記録としてそのまま残す。

| 案 | 内訳 | フォント計 | 会話中に背景へ残るタイル |
|---|---|---:|---:|
| A かな全部 | ひらがな80＋カタカナ80＋記号15 | 175 | 81 |
| B カタカナを実用集合に絞る | ひらがな80＋カタカナ29＋記号15 | 124 | 132 |
| C B＋濁点を独立タイル | ひらがな57＋カタカナ25＋記号15 | 97 | 159 |
| D B＋シナリオ名の漢字 | 124＋漢字67 | 191 | 65 |

### 案A: かな全部を持つ

- 内容: ひらがな・カタカナを清音／濁音／半濁音／小書きまで全部持つ（各80字）＋記号15。
- 利点:
  - **後から何が起きても字が足りない事態にならない。** 名前の変更・追加、外来語、擬音、
    ルビ的なカタカナ表記、すべて自由。scenario-writer に文字種の制約を意識させなくて済む。
  - 文字コード表が単純（かな配列そのまま）。ツール・辞書圧縮・デバッグ表示が作りやすい。
- 欠点:
  - **会話中の背景が 81 タイル**しか残らない。会話画面の背景は「その場の絵」を出したいところで、
    81 タイルは単色ベタ＋枠＋わずかな装飾が限界に近い。
    企画書 §2 の「プロップ層で変化を作る」思想は会話画面には及ばなくなる。
  - 使わない字（カタカナ51字相当）のために背景を50タイル捨てることになる。
- 実装コスト: **小。** 文字種の判定も予備スロット管理も不要。text-budget の割当が最も単純。

### 案B: カタカナを実用集合（29字）に絞る

- 内容: ひらがな80＋固有名詞に実際に出るカタカナ29＋記号15。
- 利点:
  - 背景に 132 タイル残る。案A比で **+51**。会話画面に場所ごとの絵が置けるようになる。
  - 台詞の書き味は案Aと変わらない（ひらがなは全部ある）。濁音は1字1タイルのまま。
- 欠点:
  - **落とし穴: 使っていないカタカナが無いので、後からキャラクター名を足せない／変えられない。**
    客将6名や G3 固有キャラ（環守の影／環兵ゼロ号）の名前を推敲で変えたくなった瞬間に詰む。
    「ベ」「プ」「ヨ」が無い状態で命名するのは、シナリオ作業としてかなり不自由である。
  - 擬音・外来語の表現手段が実質的に消える。
  - → **予備スロットを何枚確保するか**が必ず論点になる。予備を16枚取れば実質 140/116。
- 実装コスト: **中。** 文字コード表が疎になるためツール側に写像表が要る。
  scenario-writer が使えない字を書いたときに**ビルドで落とす検査**が必須（無いと化けて出る）。

### 案C: 案B ＋ 濁点・半濁点を独立タイルにする

- 内容: ひらがな57（清音46＋小書き9＋゛＋゜）＋カタカナ25＋記号15。
- 利点:
  - 背景に 159 タイル残る。案A比で **+78**。4案中もっとも背景が豊かになる。
  - **予備スロットが実質タダで手に入る**（後述のバンク境界の議論を参照）。
    案B の落とし穴（名前を足せない）に対する現実的な回答になりうる。
- 欠点:
  - **代償が字数見積もりに跳ね返る。** 濁点が独立タイルになると、
    (a) 「が」が **2セル幅**になるか、(b) 濁点を**上の行に重ねて置く**方式になる。
    - (a) を採ると、濁音の多い台詞ほど行が伸びる。**同じ台詞でも消費する幅が変わる。**
      ウィンドウの行数設計と1行字数の見積もりが案A/B とは別物になる。
    - (b) を採ると幅は変わらないが、会話ウィンドウが**2行分の高さを1行に使う**か、
      行間にタイル1枚分の余白を常に持つ必要がある。表示ルーチンも複雑になる。
  - どちらにしても **scenario-writer が書き始める前に決まっていなければならない。**
    後から (a)↔(b) を変えると全台詞の改行位置をやり直すことになる。
- 実装コスト: **大。** 描画側（text-budget / engine-dev）の実装が最も重い。
  濁音仮名 → 清音＋濁点への分解をツールで行う必要もある。

### 案D: 案B ＋ シナリオ名の漢字67字

- 内容: ひらがな80＋カタカナ29＋記号15＋漢字67 = 191。
- 利点:
  - **雰囲気が保てる。** 「沈んだ倉庫区」「第二の潮鳴り」「灯の教団」「響／錠／灼／環」は
    企画書の世界観そのものであり、かな書きにすると別の作品になる
    （「しずんだそうこく」「だいにのしおなり」）。
  - ルート名・研究系統名は分岐選択画面や研究配分画面にも出る。これらは企画書の三本柱
    （砂時計型2分岐／3研究系統）の提示面であり、読みにくさが直接ゲームの理解しやすさに響く。
- 欠点:
  - **背景が 65 タイルまで落ちる。** 会話画面はほぼ単色背景＋枠になる。
  - 漢字は 8x8 では潰れやすい。「潮」「廊」「稼」あたりは可読性が怪しく、
    **字形デザインの工数が 67字ぶん増える**（本 ADR では字形デザインは決めない）。
- **ただし前提を疑う余地がある**:
  シナリオ名・ルート名・研究系統名は**会話中に出るとは限らない**。
  シナリオ名は話の頭の**専用画面（アイキャッチ）**、研究系統名は**メニュー画面**に出すなら、
  そこは会話画面と**別の CHR バンク構成でよく、背景と取り合わない可能性がある**。
  その場合の実質的な姿は「会話中は案B（124/132）、専用画面のみ漢字バンクに差し替え」であり、
  コストの性質がまったく変わる。
  **これは engine-dev / text-budget の画面設計に依存するため、本 ADR では決めつけない。**
  主が案D に傾くなら、まず「シナリオ名を会話画面に出すか」を先に確定させる必要がある。
- 実装コスト: **中〜大。** 「専用画面のみ漢字」を採るなら画面遷移ごとの CHR バンク構成が要る。
  会話中にも漢字を出すなら実装は案B と同じだが、背景が 65 で成立するかを先に検証すべきである。

### 直交する軸: 会話ウィンドウの行だけ CHR バンクを差し替える（案の選択とは独立）

**どの案を選んでも効く。** MMC3 のスキャンライン IRQ で、画面上部（背景）と
会話ウィンドウの行とで BG バンクを差し替えれば、**フォントと背景の取り合いそのものが消える**。
会話ウィンドウが画面下部に固定であれば、上部は背景専用 256 タイル、下部はフォント専用にできる。

- 利点: 上表の「背景へ残るタイル」の制約が事実上なくなる。案A すら成立しうる。
- 欠点 / 前提:
  - **engine-dev の作業が増える。** ステータスバー分割（企画書 §7 が MMC3 を選んだ理由）と
    同じ IRQ を会話画面でも使うことになり、**分割回数と優先順位の調整**が要る。
  - 会話ウィンドウの位置が画面下部に固定される（タイル行境界に揃える必要がある）。
  - フォントを**64タイル境界に揃えて**配置する必要がある（バンク＝64タイル）。
    案B(124) → 2バンクに 4枚余り、案C(97) → 2バンクに **31枚余り**、
    案A(175) → 3バンクに 17枚余り、案D(191) → 3バンクに 1枚余り。
    **この「余り」がそのまま予備スロットになる**（案B の落とし穴への回答になりうる）。
  - 逆にバンク差し替えを**しない**なら、フォントと背景を同じバンクに混在させてよく、
    上表の生の数字（132 / 159 など）がそのまま使える。**どちらを採るかで最適な案が変わりうる。**
- 判断の分離: この軸は本 ADR で決めなくてよいが、**engine-dev に降ろすかどうかは主が決める**。
  「やらない」と決めるなら上表の数字がそのまま制約になる。

## 決定

**案A（かな全部）を採用する。漢字は使わない。**

### 1. 持つ字

| 種別 | 字数 | 内訳 |
|---|---:|---|
| ひらがな | 80 | 清音46＋濁音20＋半濁音5＋小書き9 |
| カタカナ | 80 | 同上（**46字の全部を持つ**） |
| 記号 | 約15 | 「」。、！？…ー・空白 など |
| 数字 | 10 | 0〜9 |
| **合計** | **185** | |

- **64タイル境界に揃えると 3バンク（192タイル）。予備は 7枚**である。
- **会話中に背景へ残るのは 256 − 185 = 71 タイル**である。

**起草時の表（案A = フォント175／背景81）は数字10字を計上していなかった。**
起草時の「要確認（spec-keeper）」はこれを指摘したものであり、主の「カナもすべて持つ」という決定に
数字・記号は当然含まれる。**本決定節の 185／71 を正とする。**
選択肢節の表は起草時の記録としてそのまま残すが、**以後の設計はすべて 185／71 で行うこと。**

なお記号は「約15」であり、まだ幅がある。**3バンク（192）に収まる上限は記号22字**までである。
記号が23字を超えると4バンク目が要り、背景はさらに減る。
**記号の確定は text-budget の作業であり、22字を超える場合は主に上げること。**

### 2. 漢字は1字も持たない

案D（シナリオ名の漢字67字）を採らなかった。
したがって**画面に出る文字列はすべてかな・数字・記号だけで書く**。
これは表記の問題にとどまらず、**企画書の固有名詞そのものを書き換える作業を発生させる**。
帰結節「漢字を使わないことの帰結」を参照。

### 3. 濁点は独立タイルにしない

案C を採らなかった。濁音・半濁音は**1字1タイル**である。

- **1字＝1セル幅が保証される。** 字数見積もりは素直な字数勘定でよく、
  「同じ台詞でも消費する幅が変わる」問題は起きない。
- 起草時に「ここだけは後から変えられない」と書いた論点（濁点方式）は、これで確定した。
  scenario-writer は**1字1セルの前提で字数を見積もってよい**。

### 4. カタカナを全部持つことで得たもの・失ったもの

主の「カナもすべて持つ」は、**カタカナ46字（＋濁音・半濁音・小書き）を全部持つ**という意味である。
固有名詞に実際に出る29字へ絞る案B は採らなかった。

**得たもの:**

- **後からキャラクター名・固有名詞を自由に足せる／変えられる。**
  案B の落とし穴（「ベ」「プ」「ヨ」が無い状態で命名する不自由さ、
  客将6名や G3 固有キャラの名前を推敲で変えた瞬間に詰む）が消えた。
- **scenario-writer が字の制約で表現を曲げずに済む。**
  擬音・外来語・カタカナ強調がそのまま書ける。使えない字の写像表も、
  疎な文字コード表も要らない（ツールと辞書圧縮が単純になる）。
- 予備スロットの枚数を論点にしなくてよくなった（起草時の「決めてほしいこと2」は消滅）。

**失ったもの:**

- **会話中の背景が 71 タイルしか残らない。**
  起草時の推奨だった案B の想定（背景132）から **61タイル減**である。
  71タイルは単色ベタ＋枠＋ごく少量の装飾が限界であり、
  企画書 §2 の「プロップ層で変化を作る」思想は**会話画面には及ばない**。
  **これは stage-author のタイルセット設計に直接効く。**
  会話画面の背景は「場所が分かる絵」ではなく「記号的な枠」として設計すること。

### 5. 直交軸（会話ウィンドウ行の CHR バンク差し替え）の価値が上がった

起草時に「本 ADR で決めなくてよい」とした直交軸（MMC3 スキャンライン IRQ で
画面上部と会話ウィンドウ行の BG バンクを差し替える）は、**本決定によって重要度が上がった。**

- 背景が 71 タイルまで落ちたため、**取り合いを消す手の価値が相対的に大きくなった。**
  差し替えを採れば上部は背景専用 256 タイル、下部はフォント専用にできる。
- フォント185タイルは 3バンク（192）にちょうど収まり、**バンク境界に揃える条件を満たしている。**
  差し替え方式との相性はよい。
- **71タイルで会話画面の背景が成立しないと判明した場合、この手が本命になる。**
  そのときは engine-dev にステータスバー分割との IRQ 調整（分割回数と優先順位）が降りる。
- **本 ADR ではまだ降ろさない。** 採否は engine-dev の画面設計と、
  stage-author が 71タイルで会話画面を組めるかの実地確認の後で、主が決める。

### 起草時の spec-keeper 所見（決定前。記録として残す）

> 以下は Proposed 時点の所見であり、主の決定（案A）とは異なる案を推していた。
> 判断の経緯として残す。**現行の仕様は上記の決定節である。**

> - **案B を軸に、予備スロットを 64タイル境界の余りで確保する形**を推す。
>   会話画面の背景 132 タイルは「場所が分かる絵」に足り、ひらがなは全部あるので
>   scenario-writer の書き味を損なわない。落とし穴（名前を足せない）は予備スロットで塞げる。
> - **案C は、背景 +27 タイルの見返りに対して字数見積もりの作り直しリスクが大きい。**
>   ただしバンク差し替えを採るなら 31枚の予備スロットが無料で付くため、
>   「予備スロットが欲しい」という理由だけなら案C を選ぶ価値は残る。
> - **案D は「シナリオ名を会話画面に出すか」を先に決めないと比較できない。**
>   専用画面に出すなら案D は案B の上位互換に近く、雰囲気の利得が大きい。
>   会話画面に出すなら背景 65 は厳しく、推さない。
> - **要確認事項（上記の数字10字）が各案に ±10 の幅を与えている。** 判断の前に潰したい。
> - **未検証の懸念**: 客将名の二つ名（帳簿／錘／弦／牙／炉番／灯）と「ゼロ号」の「号」は漢字である。
>   67字リストに含まれているか確認できていない。案B・C を採ると
>   **客将を「イル」「ダン」等と呼ぶしかなくなる**可能性がある。
>   含まれていなければ、案B・C の漢字ゼロ方針は**企画書 §4 の客将表の表記を変える**ことになる。
>   これは企画書の記述に触れるため、**決定後に別途 ADR か企画書の改訂が要る**。

（この「未検証の懸念」は、案A の採用により**確定した事実**になった。
二つ名の漢字が67字リストに含まれるか否かにかかわらず、**漢字は1字も持たない**ため、
客将名・G3 固有キャラ名を含むすべての固有名詞がかな表記になる。
帰結節「漢字を使わないことの帰結」を参照。）

## 帰結

### 解けるもの（本 ADR が Accepted になったことで進められる）

- **scenario-writer は台詞の確定稿と字数見積もりに進める。**
  使える字は「かな全部＋数字＋記号」であり、**1字＝1セル幅**である。
  Proposed 待ちで止めていた制約（CLAUDE.md §6）は解けた。
  ただし**漢字が使えない以上、固有名詞の置き換えが先に要る**（次節）。
- **text-budget のフォントタイル割当**は 185タイル／3バンク（予備7枚）で設計する。
  加えて、`make budget` の予算レポートに **「フォントが占めるタイル数」**と
  **「会話中に背景へ残るタイル数」**を含める必要がある（現在の `docs/budget.md` は
  CHRROM の総バイト数しか見ておらず、**本 ADR の制約を検出できない**）。
  **185／71 を閾値として検出できること。**
- **stage-author** は会話画面の背景を **71タイル**で設計する。
  起草時の案B 想定（132）から大きく減っている。**タイルセット設計の前提が変わった。**
- **engine-dev** には「会話ウィンドウ行の CHR バンク切替の要否」が残る（直交軸。決定節5）。
  71タイルで会話画面が成立しない場合の本命手段であり、**採否は主が決める。**

### 漢字を使わないことの帰結 — 企画書の固有名詞がすべて置き換え待ちになる

**本 ADR の最も重い帰結である。**

主の決定は次のとおりである（原文）。

> 漢字はつかえないので、単純に読み仮名に直すだけでなく、わかりやすく、それでいて短くて
> 雰囲気のある語への置きかえも積極的に進めたいです。

つまり「波止場の夜 → はとばのよる」のような**機械的な読み下しで済ませるのではない**。
**かなで書いたときに読みやすく、短く、雰囲気のある語に置き換える。**
読み仮名化は下限であって目標ではない。

#### 置き換えの対象（企画書の凍結記述）

以下はいずれも `docs/design-doc.md` に凍結されている固有名詞である。
**本 ADR では個々の語を決めない。** scenario-writer が案を出し、**主が選ぶ。**

| 対象 | 件数 | 現行表記 | 企画書の箇所 |
|---|---:|---|---|
| シナリオ名 | 15 | 波止場の夜／塩堤の崩れ／旧灯台／第一の潮鳴り／商館通り／尾根の砦／巡礼路／沈んだ倉庫区／工房／第二の潮鳴り／廃港／沈黙の書庫／稼働炉／海底回廊／潮の芯 | §6 シナリオ表 |
| 三勢力名 | 3 | 都市同盟／山の氏族／灯の教団 | §1 分岐構造, §3 世界観, §5 |
| 研究3系統 | 3 | 響／錠／灼 | §5 研究システム |
| 客将の二つ名 | 6 | 帳簿のイル／錘のダン／弦のモク／牙のラン／炉番のエン／灯のミオ | §4 ルート客将 |
| G3 固有キャラ | 2 | 環守の影／環兵ゼロ号 | §4 |
| 中心語 | 4 | 潮鳴り／環／機械兵／サラズ | §3 世界観, 表題 |
| 世代表記 | — | 第一世代／+28年／+55年（**画面に出るなら**） | §6 |

**注意すべき点:**

- **研究3系統（響／錠／灼）は1字の漢字である。**
  かなにすると「ひびき／じょう／しゃく」となり、**語として成立しない可能性が高い**
  （「じょう」「しゃく」は音だけでは意味が取れない）。
  3系統は企画書の三本柱に直結し、研究配分画面・突破線の提示に常時出る。
  **ここは読み下しでは済まず、語の作り直しが要る筆頭である。**
  なお **4本目を足すことは禁止**（CLAUDE.md §6）。**置き換えは3本のまま行うこと。**
- **作品名『潮鳴り三代記』そのものが対象である。** タイトル画面に出る（P8）。
- **《環》は1字であり、かな1字「わ」では他の語に埋もれる。**
  「環守の影」「環兵ゼロ号」「環を鎮める／用いる」（分岐2）すべてがこの語に依存している。
- ルート名（静／動）も1字の漢字である。分岐2の選択画面に出る。
  **上表に挙がっていないが同じ性質の問題であり、あわせて扱うこと。**

#### 語が決まったら、別 ADR で企画書を改める

**本 ADR は「漢字を使わないと決めた」ところまでである。**
個々の置き換え語が決まった時点で、**別の ADR を起こして `docs/design-doc.md` を改訂する。**
ADR なしに企画書を編集してはならない（CLAUDE.md 第2条）。

波及先:

- `docs/design-doc.md` §1・§3・§4・§5・§6 の固有名詞表記
- `data/scenario.tsv` の表示名（campaign-dev）
- `data/text/` の台詞中の固有名詞（scenario-writer）
- `data/layouts|props|gimmicks|waves/` のコメント・識別子（stage-author。**識別子は英数のままでよい**）
- **`src/` のラベル名は対象外である。** 固有名詞は `data/` にしかない（CLAUDE.md 第1条）。
  もし `src/` に固有名詞が現れているなら、それは置き換え以前に設計の失敗である。

#### 時期 — P6 のデータ投入より前に終わらせる

**シナリオ名は S1 から画面に出る。** P6（全12話のデータ投入）で `data/scenario.tsv` と
`data/text/` に流し込まれるため、**置き換えは P6 に入る前に完了していること。**
後から語を変えると、台詞中の言及・アイキャッチ・分岐選択画面の文言が連鎖して直る。

### spec-keeper の所見 — かな表記そのものが持つ3つの問題（決定ではない）

置き換えの語を決める作業とは別に、**かなだけで書くこと自体が生む問題**が3つある。
いずれも本 ADR では決めない。**主と各担当が別途判断する論点として挙げておく。**

1. **分かち書きをするかどうか。**
   かなだけの文は**語の切れ目が見えない**（「かんをしずめる」「しおなりがくる」）。
   分かち書き（語間に空白）を入れると可読性は上がるが、**1行の実効字数が減る。**
   これは会話ウィンドウの**行数設計と1行字数の見積もりに直結する**ため、
   **text-budget と engine-dev の両方に効く。**
   全台詞を書き始める前に決めること。後から入れると全台詞の改行位置がやり直しになる
   （濁点方式ほどではないが、性質は同じである）。
   空白を字として扱う以上、記号枠（決定節1の「約15」）にも影響する。

2. **同音の衝突。**
   漢字で書き分けていた語が、かなにすると区別できなくなる。
   例: 「環」と「輪」、「潮」と「汐」、「灯」と「火」。
   本作は《環》を中心語に置いており、**同音語が近くに出ると意味が取れなくなる。**
   置き換え語を選ぶ際、**単独の語としての良さだけでなく、他の中心語と衝突しないか**を見ること。
   これは scenario-writer が語を提案する時点のチェック項目である。

3. **短さと辞書圧縮は必ずしも同じ方向を向かない。**
   主の方針は「短くて雰囲気のある語」だが、**短い語ほど辞書圧縮に載りにくい。**
   1〜2字の語はトークン化しても利得が小さく（トークン1バイト vs 元2〜4バイト）、
   逆に**頻出する長い語ほど圧縮が効く**。
   企画書 §7 の「PRG 側の最大リスク: テキスト量」に効くのは後者である。
   したがって、**置き換えで語を短くすることが PRG 予算の削減になるとは限らない。**
   - 頻出する中心語（潮鳴り／環／機械兵）は、**長めでも頻度が高ければ圧縮で回収できる。**
   - 逆に、めったに出ないシナリオ名を無理に短くしても予算にはほとんど効かない。
   **短さは「読みやすさ」のために選ぶのであって、予算のために選ぶのではない。**
   この区別を text-budget と scenario-writer が共有していないと、
   「圧縮が効かないから語を伸ばす／縮める」という筋の悪い最適化が起きる。

### 確定するもの

- 文字種の集合は**仕様**であり、scenario-writer が独断で広げてはならない
  （`.claude/agents/scenario-writer.md` に既にそう書かれている）。
  字を足す要求は「何話の誰の台詞で、なぜ代替が効かないか」を添えて主に上げる。
- 文字コード表（字 → タイル番号の写像）は `src/text/`（text-budget）が持ち、
  **使えない字を含む台詞はビルドで落とす**。これが無いと化け文字が本番まで残る。
- **1字＝1セル幅**である（濁点は独立タイルにしない）。字数見積もりは素直な字数勘定でよい。
- **画面に出る文字列に漢字を含めてはならない。** これは台詞だけでなく、
  シナリオ名・メニュー・勢力名・研究系統名・タイトルのすべてに及ぶ。
- フェーズとの関係: 本決定は **P7（テキストと予算の締め）**の前提だが、
  **P6（全12話のデータ投入）で台詞が入り始める**ため、**固有名詞の置き換えは P6 に入る前**に
  終わっている必要がある（上記「時期」）。

### 後から覆す場合のコスト

- **案B/C/D → 案A**（字を増やす方向）: 背景タイルの再割当が必要。既存台詞は無傷。**中。**
- **案A → 案B/C**（字を減らす方向）: 使った字が消えるため**台詞の書き直し**が発生しうる。**大。**
- **濁点方式の変更（1字1タイル ↔ 独立タイル）**: 全台詞の**改行位置と字数見積もりをやり直す**。
  ウィンドウの行数設計にも波及する。**最大。ここだけは後から変えられないと考えた方がよい。**
- **漢字を後から足す**: フォントが 185＋N タイルになり、**N が 7 を超えた時点で4バンク目**が要る。
  背景はさらに減る。表記の統一（どこまで漢字にするか）もやり直しになる。**大。**
- **置き換え語を後から変える**: 企画書 §1・§3・§4・§5・§6 の固有名詞表記、`data/scenario.tsv` の
  表示名、`data/text/` の台詞中の言及が連鎖して直る。**P6 より前なら中、P6 以降は大。**
  だから**置き換えは P6 より前に終わらせる。**

`docs/budget.md`、`.claude/agents/scenario-writer.md`。
