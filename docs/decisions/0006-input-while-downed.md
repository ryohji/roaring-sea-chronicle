# ADR-0006: 猶予中（ダウン中）の入力の扱い

- Status: **Accepted**
- Date: 2026-09-12
- Decider: 主（人間）
- 影響範囲: action-dev, ai-dev, qa-runner, engine-dev（UI 提示）

## 文脈

ADR-0003 で**シナリオ中の操作キャラクターの交代を否定**した（出撃前に固定）。
その後 ADR-0005 で、HP が尽きてから死亡が確定するまでの**猶予（ダウン状態）**を導入した。

この2つが重なった結果、**操作キャラがダウン（猶予中）の間、プレイヤーの入力をどう扱うか**が
空白になった。交代がない以上プレイヤーは他のキャラに移れず、かといってダウン中の操作キャラは
動けない。ADR-0005 はこれを「後続の検討事項2」として挙げ、
「必要になった時点で別 ADR を Proposed で起こすこと」としていた。

本件は **P1 の action-dev に直接効く**。ADR-0005 の記述（帰結節 action-dev）は
「猶予中の操作キャラの入力の扱いは後続の検討事項2 が決まるまで確定できない」であり、
これが P1 の垂直スライス（`docs/plan.md` P1 の「ダウン（猶予中）状態と猶予タイマーの最小実装」）を
止めていた。

今回、**主が直接決定した**ため、Proposed を経ず Accepted として記録する。

関連: ADR-0003（操作キャラの切替可否）、ADR-0005（キャラクターの死亡と失敗の扱い）、
ADR-0001（セーブ方式＝バッテリー＋オートセーブ）。企画書 §4「編成規則」。

## 選択肢

ADR-0005 が挙げた候補に、「メタ操作も含めて一切受け付けない」案を加えて比較する。

### 案A: キャラクターに関する操作は無効。メタ操作は可能（採用）
- 内容: 猶予中、移動・レーン移動・攻撃・ガード等、キャラクターに関する入力は一切効かない。
  操作キャラにもパーティにも指示は出せない。ゲームの中断のようなメタ操作だけが可能。
- 利点:
  - ADR-0003（交代なし）と矛盾しない。操作対象は最後まで1名のまま。
  - action-dev の状態機械が単純。ダウン中は入力処理を丸ごと止めるだけで済む。
  - ADR-0005 が定めた「シナリオ失敗時にオートセーブから再開／ゲーム中断を選ぶ」の
    **中断**への道が、猶予中も塞がらない。
- 欠点:
  - プレイヤーが手を出せない時間が生まれる。猶予の意味が AI 仲間の蘇生行動だけに懸かる（後述）。
  - 無反応と不具合の区別がつく提示が別途要る。
- 実装コスト: 小。

### 案B: AI 任せで自動行動
- 内容: ダウン中、操作キャラを AI が引き継いで動かす。
- 利点: 画面上の見た目は止まらない。
- 欠点: **「ダウンしている」という状態と矛盾する。** HP が尽きた者が動くなら猶予の意味がない。
  ADR-0003 が避けた「元プレイヤー機を AI が引き継ぐ」問題も再燃する。
- 実装コスト: 中〜大。ai-dev と action-dev の両方に跨る。

### 案C: カーソルのみ操作可能
- 内容: キャラは動かせないが、カーソル等で仲間に指示を出せる。
- 利点: プレイヤーに「猶予中にできること」が残る。
- 欠点: **指示系統というシステムが新規に生える。** 企画書に存在しない機構であり、
  自律仲間 AI（企画書 §4「型そのものがキャラクター性」）の前提を崩す。
  6型の個性は「指示できない」ことで成立している。
- 実装コスト: 大。UI・ai-dev の受信側・入力仕様がまとめて増える。

### 案D: メタ操作も含めて全入力無効
- 内容: 猶予中は一切の入力を受け付けない。
- 利点: 最も単純。
- 欠点: 猶予が長い設定になったとき、プレイヤーがゲームを中断する手段を失う。
  ADR-0005 の「中断を選べる」と噛み合わない。
- 実装コスト: 小。

## 決定

**案A を採用する。** 具体的には次のとおり。

1. **キャラクターに関する操作は無効。**
   猶予中（ダウン中）、移動・レーン移動・攻撃・ガード等、キャラクターに関わる入力は一切効かない。
   **操作キャラにも、パーティ（自律仲間）にも指示を出せない。**
2. **メタ操作は可能。**
   ゲームの中断などのメタ操作は猶予中も受け付ける。
   ADR-0005 が定めた「シナリオ失敗時にオートセーブポイントから再開／ゲーム中断を選ぶ」の
   **中断**は、ここに含まれる。
3. **先行入力を残さない。**
   action-dev の規約は「ヒットストップ中に入力を捨てない（先行入力を保持する）」
   （`.claude/agents/action-dev.md`）だが、**猶予中はこれを適用しない。**
   猶予中に押された入力を保持すると、蘇生で復帰した瞬間に意図しない攻撃や移動が暴発する。
   **復帰時の入力状態は「何も押していない」から始める。**
   ダウン → 復帰は、先行入力保持の**例外**である。
   （ボタンを押しっぱなしで復帰した場合も、押し直すまで入力として扱わないこと。）
4. **メタ操作の範囲は、現時点では「中断」だけが確実である。**
   ポーズ画面の仕様がまだ決まっていないため、ポーズ／ステータス確認等を猶予中に許すかは**未定**とする。
   **勝手に広げないこと。** 必要になった時点で、ポーズ仕様とあわせて別途決める。

## 帰結

### action-dev（`src/action/`）

- **P1 の妨げが取れた。** ADR-0005 の後続の検討事項2 が P1 の
  「ダウン（猶予中）状態と猶予タイマーの最小実装」を止めていたが、本 ADR で解消した。
- ダウン中は入力処理を丸ごと止める。状態機械にダウン状態を足すだけで足りる。
- 先行入力バッファは、ダウンに入った時点および復帰の時点で**クリアする**。
  ヒットストップとダウンで扱いが違う点を、実装コメントに残すこと。
- メタ操作（中断）の入力だけは、ダウン中も別経路で拾う。

### 猶予の意味と ADR-0005 検討事項1 との連動（重要）

**この決定は、猶予（ダウン状態）の意味を「蘇生手段があるかどうか」に完全に依存させる。**
プレイヤーが何も操作できない以上、猶予中に事態を変えられるのは
**AI 仲間の蘇生行動だけ**である。

したがって、ADR-0005 の後続の検討事項1（蘇生手段の出所）が「用意しない」に倒れた場合、
**操作キャラの猶予は、結果を眺めるだけの時間になる。**
その場合は猶予自体を短くするか、猶予を設けずに即シナリオ失敗とする方が誠実である。

**これは主が決める論点であり、本 ADR では決めない。ADR-0005 の検討事項1 と連動する。**
本 ADR によって検討事項1 の優先度は上がった。

#### 追記（2026-09-12）— ADR-0007 による解決と、残った区間

ADR-0005 の検討事項1 は
[ADR-0007「蘇生手段 — クールタイムつきの共有アイテム」](0007-revive-item.md) で解決した。
蘇生手段は用意される（**クールタイムつきのパーティ共有アイテム／あるシナリオの通過で入手**）ため、
上の「用意しない」の場合は成立しない。

**ただし、この指摘は蘇生アイテムの入手前のシナリオでは依然として成立する。**
入手フラグが立つまでは蘇生手段が存在せず、操作キャラの猶予は結果を眺めるだけの時間のままである。
入手シナリオが後半に置かれれば、S1〜S4 の猶予に意味はない。
**入手時期を早めるか、入手前は猶予を短く（あるいは猶予なしに）するか**は
主が決める論点として残っている（→ ADR-0007「入手時期」）。
どのシナリオで入手するかは ADR-0007 でも決めていない。

また、本 ADR の決定1（猶予中はパーティにも指示を出せない）から、
**操作キャラのダウン中に蘇生アイテムを使えるのは自律仲間（AI）だけ**であることが導かれる。
これは ADR-0007 が新たに決めたことではなく、本 ADR の帰結である（→ ADR-0007 帰結節）。

### ai-dev（`src/ai/`, `data/ai_params.tsv`）

- 操作キャラがダウンしている間、**仲間 AI の行動が唯一の変数になる。**
  庇護型が助けに向かうのか、突撃型はそのまま戦い続けるのか。
- 具体的な行動は蘇生手段（ADR-0005 検討事項1）が決まるまで確定できない。
  しかし、**「操作キャラがダウン中」という状況を AI の状況評価の入力に持つ必要がある**ことは
  今決まる。型ごとの反応差はパラメータ表側で表現すること（型ごとに別コードを書かない）。
  - **追記（2026-09-12）**: 蘇生手段は [ADR-0007](0007-revive-item.md) で決まった。
    その状況で取る行動は**蘇生アイテムの使用**であり、実装対象になった。
    **どの型が使うかは ADR-0007 でも未決**である。

### qa-runner（`test/`）

- 代表20経路とは別に、単体的な検証項目が2つ増える。
  1. **猶予中に入力を送っても操作キャラが動かないこと**（移動・攻撃いずれも）。
  2. **復帰時に先行入力が暴発しないこと**（猶予中にボタンを押し続け、蘇生直後の1〜数フレームで
     攻撃・移動が発生しないこと）。
- いずれも入力列で再現できるため、Mesen Lua でも `test/harness/` の Python 6502 エミュレータでも
  検証しうる。

### UI への含み

プレイヤーが「今は何をしても動かない」と分かる提示が要る（猶予の残り時間の表示など）。
**無反応は不具合と区別がつかない。**
具体的な表現は決めない。P1（最小の提示）と P8（仕上げ）の課題として挙げるに留める。

### engine-dev

- 直接の影響はない。ダウン中のスプライト優先度は ADR-0005 の記述（クラス3相当）のまま。

### 企画書への波及

- なし。企画書 §4 の記述（ダウン／猶予／シナリオ失敗／戦線離脱）は本 ADR で変わらない。
- 三本柱（砂時計型2分岐／3層差分／家系継承）には触れていない。

### 後から覆す場合のコスト

- 案C（カーソル／指示）に移る場合は高い。指示 UI・ai-dev の受信側・入力仕様が同時に生え、
  自律仲間 AI の前提（指示できないから型が個性になる）を組み直すことになる。
- 案B（AI 任せ）に移る場合も高い。ADR-0003 が避けた状態引き継ぎ問題が戻る。
- 案D（メタ操作も無効）へは安い。中断の受付を外すだけ。
- 先行入力の例外（本決定3）だけを覆すのは安いが、覆す理由は考えにくい。
