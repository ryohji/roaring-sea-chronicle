# ADR-0009: 擬似奥行きからレーンを廃止する

- Status: **Accepted**
- Date: 2026-09-19
- Decider: 主（人間）
- 影響範囲: engine-dev, action-dev, ai-dev, qa-runner, stage-author（確認のみ）／
  `src/engine/lane.s`, `src/action/`, `src/ai/`, `test/`, `docs/design-doc.md`, `docs/plan.md`, `CLAUDE.md` 第5条

## 文脈

### 発端

**P1（垂直スライス）の受入で、主が実機で操作し「なにも楽しさが感じられない」と判断した。**
P1 の受入条件は「主が実際に操作して『面白い』と判断すること」であり、**この条件は満たされていない。**

指摘は6件あった。うち5件は描画側の不足（向き・姿勢・役割・当たり判定・影が画面に出ていない）で、
本 ADR の対象外（別途対応中）。残る1件が本件である。

> 横方向の移動にはない制限が縦方向にはかかるという**レーンの制限がそもそも理不尽に感じられます**。

spec-keeper から主への回答として、縦移動には横移動に無い制約が**3つ重なっている**ことを示した。

1. 動きが4段階に**量子化**される（`LANE_COUNT = 4`、`lane_ground_y` 表）
2. 移動が `LANE_MOVE_FRAMES = 8` フレームかけて**補間**される（即応しない）
3. **補間中の入力が捨てられる**（`src/action/player.s` は `ent_lane_step != 0` の間、上下入力を無視する）

さらに 4点目として、`ACT_LANE_REACH = 0`（`src/action/action_params.inc`）により
**同一レーンでないと攻撃が当たらない**。横方向には「だいたい合っていれば当たる」のに、
縦方向は「完全一致でなければ当たらない」。理不尽さの中心はここにある。

これに対する主の決定が本 ADR である。

> レーンの導入は、もともとキャラクターを構成するスプライトの量を制限するためだったとおもいます。
> **このレーンの存在自体を無くしたほうがよい**と考えています。

### 事実確認 —— レーンの導入理由と、スプライト量との関係

決定そのものより先に、**前提を事実に合わせて記録しておく。**
後から本 ADR を読む者が「レーンを廃止するとスプライトが増える」と誤解しないためである。

**(1) レーンはスプライト量の制限のために導入されたのではない。**

文書上の根拠は企画書 §9 リスク表の1行だけであり、そこにはこうある。

> | 擬似奥行きの当たり判定が曖昧 | **レーン数を4に固定**。レーン間の攻撃可否を早期に仕様確定（垂直スライスの受入条件） |

つまり導入理由は **当たり判定の曖昧さ対策**である。スプライトの話は同じ表の**別の行**にあり、
そちらの対策は「1スキャンライン8スプライト制約を前提に AI の配置分散を実装。敵同時数を先に決める」で、
レーンには触れていない。`src/engine/lane.s` の冒頭注記にも、スプライト量への言及は無い。

**(2) レーンはスプライト量を1つも減らしていない。**

同時表示数を決めているのは `MAX_ENEMIES = 6`（ADR-0002）と、
1スキャンラインあたり8スプライトというハードウェアの制約である。レーンはどちらにも関与しない。
レーンがあってもなくても、画面に居るキャラクターの数も、1体あたりのスプライト数も変わらない。

**(3) レーンは8スプライト制約を、むしろ悪化させる側だった。**

Y が4値に量子化されるため、複数のキャラクターが**まったく同じ Y に揃いやすい**。
同じ Y に揃うことは、1スキャンライン8スプライト制約にとって最悪のケースである。
奥行きを連続にすれば完全一致は稀になる。

ただし**改善は限定的である。過大に評価してはならない。**
16ドット高のスプライトは、隣接レーン間隔（12 / 16 / 20 ドット）でも走査線を共有する。
連続にしても、近くに立つキャラクター同士が同じ走査線に載ることは変わらない。
正確には「**損はしない。最悪ケース（完全一致）がわずかに減る**」程度である。
ADR-0002 の重み付きスプライト巡回（P2）の重要度は、本 ADR によって下がらない。

**(4) 前提の誤りは、決定の妥当性を損なわない。**

主の前提（スプライト量のため）は事実と異なるが、**決定は妥当である。**理由は2つ。

- 本来の導入理由である「当たり判定の曖昧さ」は、**レーンでなくても解ける。**
  当たり判定を「足元Yの近さ（許容幅つき）」で行えば、曖昧さは残らない。
  曖昧さの正体は「奥行きが連続だと何ドットまで当たるのか決まっていない」ことであって、
  「奥行きが連続であること」そのものではない。レーンは解法の一つに過ぎず、唯一の解ではない。
- 上に挙げた**制約3つの重なりは、レーンを保ったままでは完全には解消できない。**
  量子化そのものが「上を押しても、次の段まで行かないと何も起きない」を生む。

関連: ADR-0002（敵同時数と重み付き巡回）、ADR-0005（猶予）、ADR-0006（猶予中の入力）。
企画書 §1、§9 リスク表。CLAUDE.md 第5条（レーン数は4に固定）。

## 選択肢

### 案A: レーン4本を維持し、当たり判定にY許容幅を足す

- 内容: `ACT_LANE_REACH` を「レーン差」ではなく「足元Yの許容幅」に読み替え、
  レーン間でも Y が近ければ当たるようにする。移動系（量子化・補間・入力破棄）はそのまま。
  spec-keeper が主に最初に提案した折衷案である。
- 利点: 変更が `src/action/combat.s` と `action_params.inc` に閉じる。`lane.s` に触らない。
  当たらない理不尽（上記4点目）だけは消える。P1 の他5件の修正と並行できる。
- 欠点: **理不尽の中心3つ（量子化・補間・入力破棄）が残る。**
  むしろ悪化する面がある。Y許容幅を広げるほど「レーンを合わせる操作」に意味が無くなり、
  それでも移動だけは4段階に量子化され続ける。**制約だけ残って見返りが消える。**
  「離散の奥行きは、レーンを合わせる操作に意味があるときだけ働く」という
  `action_params.inc` の既存の説明が、そのまま案Aの否定になっている。
- 実装コスト: 小（1〜2ファイル、半日）。ただし**手触りの問題を解いていない**ので、
  P1 の受入は通らない見込みが高い。

### 案B: レーンを廃止し、奥行きを連続にする（**採用**）

- 内容: 量子化・補間・入力破棄・レーン一致判定の4つをまとめて捨てる。
  上下入力で足元Yが連続に動き、当たり判定は足元Yの近さで行う。
- 利点: **理不尽の原因4つが同時に消える。**縦と横が同じ性質の操作になる（連続・即応・許容幅つき判定）。
  コードが減る（`lane.s` の補間状態機械、`ent_lane*` の作業変数4本、combat.s の補間中救済）。
  **作業変数を更新途中に読む脆さ**（qa-runner で何度も問題になった）の主要因が消える。
  8スプライト制約に対しては、わずかだが損はしない（上記事実確認(3)）。
- 欠点: **企画書の §1 と §9 に手が入る。**CLAUDE.md 第5条を主が書き換える必要がある。
  engine / action / ai / test の4担当に同時に波及し、**並行作業の調整が要る**
  （いま engine-dev が `src/engine/` を触っている）。
  「立ち位置を合わせる読み合い」という離散ならではの駆け引きは失われる。
  ただし P1 の実機評価では、その駆け引きは**そもそも成立していなかった。**
- 実装コスト: 中。`lane.s` の大半を削除し `ent_y` のクランプに置き換え、
  combat.s / ai.s の判定をYの距離に差し替え、test の L2 を書き直す。
  **純減の変更**なので、コード量は増えない見込み。

### 案C: レーンを維持したまま、補間を短くし、補間中の入力を予約できるようにする

- 内容: `LANE_MOVE_FRAMES` を 8 から 3〜4 に縮め、補間中の上下入力を捨てずに
  「次の移動」として1つだけ予約する。当たり判定は案Aの許容幅も併用する。
- 利点: レーン（と企画書の記述、CLAUDE.md 第5条）を維持したまま、
  理不尽の3つ目（入力破棄）と2つ目（もたつき）を緩和できる。ADR の波及が小さい。
- 欠点: **1つ目（量子化）が残る。**「上を押した量に応じて動く」にはならない。
  加えて**入力予約キューという新しい状態**が増える。作業変数を増やす方向であり、
  qa-runner が繰り返し踏んだ「更新途中の作業変数を読む」脆さを悪化させる。
  補間を縮めると、`lane.s` の「移動の途中で前後関係が入れ替わるのが自然に起きる」という
  設計上の狙い（奥行きの説得力）も薄れ、**レーンを保つ理由自体が痩せる。**
- 実装コスト: 中（案Bと大差ない）。**コストが同等で、得られるものが少ない。**

## 決定

**レーン（4段階の量子化）を廃止し、擬似奥行きを連続にする。**（案B）

1. **上下入力で足元Yが連続に動く。** レーン番号という概念を持たない。
   移動はフレーム単位で即応し、補間という状態を持たない。入力を捨てる区間が無くなる。
2. **当たり判定は「足元Yの近さ」で行う。** レーン番号の一致ではない。
   **許容幅はパラメータ**とし、`src/action/action_params.inc` に置く（action-dev の持ち分）。
3. **奥行きの移動速度は、横移動と別の値を持てる。**
   ベルトスクロールの慣習では奥行きの方が遅い。
   **具体値はこの ADR では決めない。** action-dev と主の調整対象である。
4. 擬似奥行きそのもの（横から見た画面で上下に動き、足元Yで前後が決まる）は**維持する。**
   廃止するのはレーン＝量子化であって、奥行きではない。

## 帰結

### engine-dev（`src/engine/`）

- `src/engine/lane.s` の**補間の状態機械が不要になる。**
  作業変数 `ent_lane_step` / `ent_lane_acc` / `ent_lane_dy`、および `ent_lane` / `ent_lane_from` を
  エンティティ表から落とせる（`src/engine/entity.s`）。
  `lane_ground_y` 表と `lane_distance`、`lane_y_of`、`ent_lane_move`、`lane_update_all` も不要。
- 代わりに **`ent_y` が「歩ける帯」の上下限でクランプされる形**になる。
  定数は `src/constants.inc`（`LANE_COUNT` / `LANE_FIRST` / `LANE_LAST` / `LANE_MOVE_FRAMES` の置き換え）。
- **前後関係の判定は変更が要らない。**
  `src/engine/sprite.s` の `oam_sort_order` は既に「補間後の足元Y（`ent_y`）」を並べ替えキーにしており、
  レーン番号を見ていない。**ここは触らなくてよい。**
  同じく「移動の途中で前後関係が入れ替わる」という挙動も、連続化でそのまま保たれる（むしろ滑らかになる）。
- メインループ（`src/main.s`）から `lane_update_all` の呼び出しが消える。
  AI が「レーン移動を頼む → 同じフレームで動き出す」ために守っていた呼び出し順の制約も消える。

### action-dev（`src/action/`）

- **`ACT_LANE_REACH` が「Y許容幅」に置き換わる。**
  `action_params.inc` §1 の説明文（0 = 同一レーンのみ / 1 = 隣接まで、上限1に縛る）は全面的に書き直す。
- **「レーン補間中は出発レーンと目標レーンの両方に居るとみなす」救済が不要になる。**
  `src/action/combat.s` の `act_lane_ok`（`ent_lane_from` / `ent_lane_step` を見る分岐）は丸ごと消える。
  **そもそも補間という状態が消えるためである。**
- `src/action/player.s` の `act_player_lane`（上下でレーンを1つ移す、補間中は入力を捨てる）は、
  `ent_y` を速度ぶん動かしてクランプする処理に置き換わる。
- 新しいノブは2つ:**奥行きの移動速度**と**当たり判定のY許容幅**。どちらも `action_params.inc` に置く。
- 手触りの評価は許容幅と速度の組で決まる。**この2値が P1 の再受入の主対象になる。**

### ai-dev（`src/ai/`, `data/ai_params.tsv`）

- `lane_hold`（レーン移動の積極性＝次にレーンを移れるまでの最短フレーム数）は、
  **奥行き方向の追従に関するパラメータ**に意味が変わる。列名の変更を伴う。
- 攻撃性・標的選択の重みづけにある **「レーン差 × AI_LANE_COST(8)」（`src/ai/ai.s`）が、
  Y の距離そのものに置き換わる。** `lane_distance` の呼び出しは無くなる。
- `reach_x`（`data/ai_params.tsv`）の説明「標的がこの距離以内・**同じレーン**なら振る」は
  「Y許容幅以内なら振る」に改める。
- **型ごとの分岐は無い。** 6型すべてが同じ機構を使い、**パラメータの意味が変わるだけ**である。
  AI の型設計（ADR 未起票）には影響しない。
- 「action の持ち分（`ACT_LANE_REACH`）を AI が知って振る舞いを変えてはならない」という
  `ai.s` の既存の境界は、そのまま「Y許容幅を AI が知らない」として維持する。

### qa-runner（`test/`）

- **レーン補間・レーン番号のクランプの検証が丸ごと不要になる。**
  `test/l2_engine.py` の `_check_lane_interpolation` / `_check_lane_distance`、
  および「レーン数が4固定である」「`lane_ground_y` が奥→手前で単調増加する」の検査は削除する。
  `test/scene.py` のエンティティ表定義（`ENT_FIELDS` の `ent_lane*` 5本）と
  `place(..., lane=0)` の引数も落ちる。
- 代わりに要る検証は2つ。
  1. **奥行きの上下限**（`ent_y` が歩ける帯の外に出ないこと。上下端で張り付いても壊れないこと）
  2. **Y許容幅での当たり判定**（境界値ちょうど、境界の±1。横の矩形判定との組み合わせ）
- **補間の作業変数を更新途中に読む脆さが何度も問題になったが、その主要因が消える。**
  `ent_lane_step` / `ent_lane_acc` / `ent_lane_dy` は「フレームの途中でだけ意味を持つ」変数であり、
  テストが観測する時点によって値が変わった。連続化後の `ent_y` は**常に確定した現在位置**である。
  ADR-0004（テストハーネス）の「更新の途中を覗かない」という約束は維持するが、守りやすくなる。

### stage-author（`src/stage/`, `data/`）

- **ルート固有ギミック3種は、いずれもレーン番号に依存していない。**
  企画書 §2 のギミック表を確認した結果は次のとおり。
  - 都市同盟「滑車と吊り荷」— 可動床になる／切り落として質量武器にする／敵を押し潰す。
    位置と落下の当たり判定であり、レーン番号の語は無い。
  - 山の氏族「獣の呼び寄せ・崩落足場」— 獣を誘導して敵に当てる／足場が踏むと落ちる。
    「踏む」は接地位置の判定であり、**足元Yの近さで表現できる。**レーン番号は不要。
  - 灯の教団「灯火」— 光が当たった機械兵が起動／消すと停止。明暗が攻略リソース。
    光の届く範囲であり、連続の方がむしろ自然に書ける。
- **依存していない。**したがって、ギミック層の設計見直しは**要らない。**
  ギミックのデータ形式（P3）は、奥行き位置を**レーン番号ではなく Y 値**で持つこと。
  `data/gimmicks/` はまだ空であり、P3 未着手のため**手戻りはゼロ**である。
- なお `data/text/outline.md` の S1 解説に「4レーンの移動、レーン間の攻撃可否を覚える」という
  記述がある（45行目）。これは scenario-writer の持ち分なので、**本 ADR では改めない。**
  語の置き換え（下記）のときに一緒に直す。

### 覆す場合のコスト

レーンに戻すには、`lane.s` の補間状態機械とエンティティ表の作業変数5本を復活させ、
combat.s の補間中救済と ai.s のレーン差コストを書き戻すことになる。
削除した L2 テストの再作成も要る。**中程度のコストだが、不可能ではない。**
ただし、戻す判断をするなら**その前に、案A（許容幅の併用）を試すべきである。**
レーンの理不尽さは量子化そのものに由来しており、単純に戻しても P1 の指摘は再発する。

## 企画書への波及（**今回は改めない。列挙に留める**）

`docs/design-doc.md` は凍結文書であり、本 ADR は「何を改める必要があるか」を確定させるに留める。
実際の改訂は下記「改訂の束ね方」の判断を主が下してから行う。

`grep -n "レーン\|奥行き" docs/design-doc.md` の結果は3箇所。うち改訂が要るのは2箇所である。

| **250** | §9 リスク表「擬似奥行きの当たり判定が曖昧 → **レーン数を4に固定**。レーン間の攻撃可否を早期に仕様確定（垂直スライスの受入条件）」 | **対策そのものが変わる。**「足元Yの近さ＋許容幅で判定。許容幅と奥行き速度をパラメータ化し、実機で調整する」。受入条件の書き方も P1 の再定義に合わせる |
| 44 | プロップ層の例「旗→裂けた旗、**クレーン**→倒壊クレーン」 | **変更不要。**「クレーン」は荷役機械であってレーンとは無関係 |

### 改訂の束ね方 —— 語の置き換え（ADR-0008 関連）と一緒にやるか

**一緒にやる方が安い可能性が高い。**判断材料を挙げる。

- ADR-0008（文字種＝かな全部・漢字ゼロ）により、企画書の固有名詞の**かな置き換えが P6 の前提**である。
  対象はシナリオ名・三勢力・研究3系統・客将の二つ名・中心語・ルート名・作品名。
  これは §1 を含む企画書の広い範囲に手が入る、**大きな1回の改訂**になる。
- 本 ADR が要求する改訂は **2箇所・数行**である。単独で改訂を1回起こすには軽い。
- 凍結文書の改訂回数は少ない方がよい（改訂のたびに全エージェントの読み直しと差分追跡が要る）。
- **ただし、束ねるなら条件が2つある。**
  1. **語の決定を待つ間、企画書 §9 の「レーン数を4に固定」が残り続ける。**
     これは**本 ADR に反する記述が凍結文書に残る**状態である。
     P1 をやり直す engine-dev / action-dev が §9 を読んで混乱しうる。
     束ねる場合は、**§9 の当該行に「ADR-0009 により置き換え済み」の1行注記だけは先に入れる**こと。
     注記だけなら改訂ではなく追記であり、語の決定を待たずに打てる。
  2. 語の置き換えは「語が決まるまで企画書は改めない」（CLAUDE.md §6）で止まっている。
     **語がいつ決まるか未定なら、束ねるのは危険である。**待ち時間が読めないなら本 ADR 分を先に打つ。
- **推奨**: 語の決定が P6 より十分前に見込めるなら**束ねる**（注記は先に打つ）。
  見込めないなら **§1 と §9 の2箇所だけ先に改訂する**。この判断は主が下す。

## 残る論点（本 ADR では決めない）

1. **奥行きの許容幅と移動速度の具体値。**
   action-dev が `action_params.inc` に置き、主が実機で調整する。
   許容幅を広げるほど当てやすくなるが、奥行きの意味が薄れる。
   速度は横移動（`ACT_MOVE_SPEED = 24`＝1.5ドット/f）より遅い値が慣習だが、
   **P1 の指摘が「縦だけ制限がある」だった以上、遅くしすぎると同じ苦情に戻りうる。**
2. **歩ける帯の上下限**（画面のどこからどこまでが床か）。
   現在の `lane_ground_y` は 148〜196 で、上端に**上部ステータスバー（MMC3 スキャンライン IRQ で分割）**と
   遠景、下端に手前側の前景ぶんの余白を取ってある。
   **ステータスバーの位置・高さが決まらないと上限が決まらない。**engine-dev と主の調整対象。
   なお 148〜196 をそのまま帯にすると、帯の高さは 48 ドットしかない。
   連続化を活かすなら広げたいが、広げるほど背景の余白を食う。**これは奥行きの見え方に直結する。**
3. **8スプライト制約への影響の再評価。**
   連続にすると「まったく同じYに揃う」ことは減るが、
   **プレイヤーが敵と同じ高さに並ぶ状況そのものは変わらない**（むしろ戦闘の基本形である）。
   16ドット高のスプライトは近接していれば走査線を共有する。
   **ADR-0002 の重み付き巡回（P2）の重要度は下がらない。**本 ADR を理由に P2 を軽くしてはならない。
4. 奥行き方向にも慣性・加速を入れるか（横移動と揃えるか）。
   現在の横移動が等速なら、奥行きも等速で始めるのが素直である。action-dev の判断。
