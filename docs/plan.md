## 1. 技術スタック

| 領域 | 採用 | 理由 |
|---|---|---|
| アセンブラ | **ca65 / ld65**（cc65） | NES開発の事実上の標準。リンカスクリプトでバンク管理が明示できる |
| マッパー | **MMC3（Mapper 4）** | PRG 256KB / CHR 128KB。スキャンラインIRQでステータスバー分割 |
| ビルド | **Make + Python 3** | データテーブル→バイナリ変換をPythonで、全体をMakeで |
| エミュレータ | **Mesen2**（Lua スクリプティング） | ヘッドレス実行＋Luaで入力再生と状態検証ができ、CIに載る |
| CHR作成 | PNG → Python変換スクリプト | 画像を正とし、リポジトリでdiffが見える |
| バージョン管理 | Git | ROMはビルド生成物としてコミットしない |

## 3. CLAUDE.md の要点（リポジトリ憲法）

これは全エージェントが毎回読む前提の文書。以下を必ず含める。

1. **物語を6502コードに書かない。** シナリオ・ロスター・台詞・プロップは必ず `data/` のテーブル経由。
2. **企画書は凍結文書。** 実装都合で仕様を変えたくなったら、コードを変える前に `docs/decisions/` にADRを起こす。
3. **キャラクターの個性はグルド家以外では揺らさない。** ルート差分の台詞を他家系に追加してはならない。
4. **ROM予算は制約ではなく設計対象。** `make budget` が予算超過を検出したら、機能追加より削減を優先。
5. **レーン数は4に固定。** 擬似奥行きの仕様変更はプロジェクト全体に波及するため、ADRなしに触らない。
   → **ADR-0009（Accepted）でレーンそのものを廃止した。**奥行きは連続になる。
   この第5条の文面は主が `CLAUDE.md` 側で書き換える。本行はそれに追随する（spec-keeper が勝手に直さない）。
6. コミットは1論点1コミット。ROMバイナリはコミットしない。
7. 実装したら必ず `make test` を通す。落ちたまま次の作業に進まない。

## 4. エージェントチーム編成

Claude Code のサブエージェントとして 7 体を定義する。役割を狭く切り、コンテキストの衝突を避ける。

### 4.1 spec-keeper（仕様管理）

- **担当**: 企画書と実装の整合、ADRの起草、用語の統一
- **権限**: `docs/` のみ書込可。`src/` は読取のみ
- **起動タイミング**: 仕様に迷いが出たとき、仕様変更が発生したとき
- **なぜ必要か**: 12話 × 2分岐 × 3研究系統の整合は人間の記憶では保たない。単一の真実源を維持する番人が要る

### 4.2 engine-dev（コアエンジン）

- **担当**: PPU制御、横スクロール、**擬似奥行き（連続。ADR-0009 でレーン廃止）**、スプライト割当、当たり判定、MMC3バンク切替
- **範囲**: `src/engine/`
- **成功条件**: 1スキャンライン8スプライト制約下で、プレイヤー1＋仲間2＋**敵6**を、
  優先度つき巡回で「操作キャラと弾は欠けさせない」形で描く（ADR-0002 により敵4→6、フリッカー許容に変更）

### 4.3 action-dev（アクション）

- **担当**: プレイヤー操作、攻撃判定、ヒットストップ、ノックバック、**奥行きの当たり判定（足元Yの許容幅。ADR-0009）**
- **範囲**: `src/action/`
- **ダウン（猶予中）はキャラクターに関する入力を無効にし、先行入力も保持しない**
  （ヒットストップと違い、復帰時は「何も押していない」状態から始める。ADR-0006）
- **成功条件**: 手触りの評価はこのエージェントに任せず、必ず人間（主）が実機/エミュで確認

### 4.4 ai-dev（自律仲間AI）

- **担当**: 6型（突撃/牽制/回収/庇護/遠隔/万能）の行動ロジック、AI攻撃性パラメータ、
  **蘇生アイテムの使用行動**（操作キャラのダウン中に使えるのは自律仲間だけ。ADR-0006・ADR-0007）
- **範囲**: `src/ai/`
- **成功条件**: 型を見分けられる。プレイヤーの邪魔をしない（壁になって進行不能にしない）
- **注意**: 型の個性は**パラメータ表**で表現し、型ごとに別コードを書き散らさない

### 4.5 campaign-dev（キャンペーン基盤）

- **担当**: フラグ管理、分岐判定、世代継承（縁値・恒久離脱・客将繰り上げ）、研究配分、セーブ（バッテリー＋オートセーブ。ADR-0001）
- **範囲**: `src/campaign/`, `data/flags.tsv`
- **成功条件**: プール下限5名が全経路で保証される（詰みが起きない）
- **蘇生アイテムの入手フラグと入手シナリオ**をデータで定義する（ADR-0007）。
  クールタイムの残りをセーブに含めるかは P4 の判断事項

### 4.6 stage-author（ステージオーサリング）

- **担当**: レイアウト、プロップ層、ギミック層、敵ウェーブ、およびそれらのビルドツール
- **範囲**: `src/stage/`, `data/layouts|props|gimmicks|waves/`, `tools/`
- **成功条件**: 同一レイアウト＋ギミック差し替えで3ルート分の遊びが成立する（S6で検証）

### 4.7 text-budget（テキストと予算）

- **担当**: 辞書圧縮、台詞テンプレート、`make budget` によるPRG/CHR予算計測とレポート
- **範囲**: `src/text/`, `data/text/`, `docs/budget.md`
- **成功条件**: 全テキストが予算内。超過時はCIを落とす
- **なぜ独立させるか**: 予算監視を実装者本人に兼任させると必ず甘くなる

### 4.8 qa-runner（回帰テスト）

- **担当**: Mesen Lua による自動プレイ、**代表20経路**の回帰、クラッシュ検出
- **範囲**: `test/`
- **成功条件**: 全経路がクラッシュせず最終話に到達する

## 5. 作業計画（フェーズ制）

各フェーズは**受入条件を満たすまで次に進まない**。垂直スライスを最優先にする。

### P0 — 環境と骨格（最小の動くROM）

- cc65 / Mesen2 / Python 環境構築、Makefile、MMC3リンカスクリプト
- 黒画面に1スプライトが出るROMをビルドし、Lua自動テストが通る
- `CLAUDE.md`、`docs/design-doc.md`（本企画書）を配置
- **受入**: `make && make test` がクリーンに通る

### P1 — 垂直スライス（S1 が遊べる）

ここが最大の山。ここで手触りが決まる。

- **連続の擬似奥行き移動**（上下入力で足元Yが連続に動く。ADR-0009 でレーンを廃止）、横スクロール、プレイヤー攻撃
- 自律仲間1体（万能型）、敵1種
- スプライト割当は**単純な優先度順**で実装する（重み付き巡回は P2。ADR-0002）
- **ダウン（猶予中）状態と猶予タイマー**の最小実装。猶予の長さはパラメータ（ADR-0005）
- **猶予中の入力**: キャラクターに関する操作は無効、メタ操作（中断）のみ可能。
  猶予中は先行入力を保持せず、復帰時は「何も押していない」状態から始める（ADR-0006）。
  → これで **action-dev 側の未決（ADR-0005 の後続の検討事項2）は解消済み**。P1 に入ってよい
- 猶予中であることの最小限の提示（無反応と不具合が区別できること）。表現の作り込みは P8
- **蘇生アイテムは P1 に載せない**（ADR-0007）。P1 の猶予は必ず切れる前提でよい。
  action-dev 側の復帰処理（復帰演出・先行入力を持ち越さない）は P1 で作るが、
  それを起動する蘇生行動は **P2 の ai-dev**（AI が使う）に載る
- **S1「波止場の夜」を通しでクリアできる**
- **受入**: 主が実際に操作して「面白い」と判断すること。ここで詰まったら先に進まない

#### P1 は受入未達である（2026-09-19）

**主が実機で操作し、「なにも楽しさが感じられない」と判断した。** 受入条件は満たされていない。
**P2 に進んではならない。** 指摘は6件。

- 5件は**描画側の不足**（向き・姿勢・役割・当たり判定・影が画面に出ていない）。別途対応中
- 1件は**レーンの理不尽さ** → **ADR-0009（Accepted）でレーンを廃止**した

##### 受入条件の置き換え（ADR-0009）

企画書 §9 リスク表および本フェーズの「**レーン間の攻撃可否を早期に仕様確定**」は、
レーンの廃止により**そのままでは成立しない。** 次の形に置き換える。

- **奥行きの当たり判定を「足元Yの近さ＋許容幅」で仕様確定する**（レーン差の比較ではない）。
  許容幅は `src/action/action_params.inc` のパラメータとして置き、**主が実機で決める**
- **奥行きの移動速度**を同じくパラメータとして置き、主が実機で決める（横移動と別の値を持てる）
- **奥行きの上下限（歩ける帯）**を確定する。上端はステータスバーの位置に依存する（ADR-0009 残論点2）

**「レーン間の攻撃可否」という論点は消滅した。**代わりに上の3点が P1 の再受入の対象である。
なお **ADR-0002 の重み付きスプライト巡回（P2）の重要度は下がらない**（ADR-0009 残論点3）。

### P2 — パーティ3名と自律AI

- 3名出撃、操作キャラ切替なし（出撃前に選択）
- AI 6型すべて実装、パラメータ表化
- **AI の「蘇生アイテムを使う」行動**（ADR-0007）。操作キャラがダウン（猶予中）のとき、
  プレイヤーは操作できない（ADR-0006）ため、**使えるのは自律仲間だけ**である。
  **どの型が使うかは未決**（ADR-0007）。決まるまで型ごとの優先度をパラメータに入れない
  - 蘇生アイテムはパーティ共有・クールタイムつき。**クールタイムの長さはパラメータ**（データ側）。
    入手前は使えない（入手フラグは P4 で `data/flags.tsv`。P2 では常に入手済みとして検証してよい）
  - 蘇生に向かう行動が「壁になって進行不能にしない」を壊さないこと（全員が群がらない）
- スプライト割当の優先度制御（欠けの緩和）
- **重み付きスプライト巡回の実験**（クラス0〜4、高優先度を複数回。敵同時6体。ADR-0002）
  ちらつきの評価は L2 では不可。Mesen2（L3）か実機で主が見る
- 戦線離脱（AI キャラの猶予切れ）とその演出。離脱しても進行不能にならないこと（ADR-0005）
- **受入**: 型ごとに戦闘の手触りが違うと分かる

### P3 — ステージオーサリング基盤

- レイアウト／プロップ層／ギミック層のデータ形式確定とローダ
- ルート固有ギミック3種（滑車・獣と崩落・灯火）
- **S2 と S6 を実装**。S6で「同一レイアウト×3ギミック」を検証
- **受入**: 新規ステージ1本の追加が、コード変更なしにデータ追加だけで完了する

### P4 — キャンペーン基盤

- フラグ、分岐1（S3）、世代交代（S4）、縁値と継承、選択イベントによる恒久離脱、客将繰り上げ
- セーブ方式の決定（ADR-0001 で決定済み: バッテリー＋オートセーブ）
- **オートセーブの実装**: PRG-RAM $6000-$7FFF、チェックサム、破損時フォールバック、
  書き込み中の電源断でデータを壊さないこと（二面バッファ or 書き込み完了フラグ）。
  オートセーブポイントは `data/scenario.tsv` で定義（ADR-0001）
- **シナリオ失敗 → 直前のオートセーブポイントから再開**の経路（ADR-0005）
- **蘇生アイテムの入手フラグ**（`data/flags.tsv`）と**入手シナリオ**（`data/scenario.tsv`）の定義（ADR-0007）。
  入手済みはセーブ対象（シナリオをまたぐ恒久的な状態）。コードに話番号を書かない
  - **判断事項**: **クールタイムの残りをセーブに含めるか。**
    オートセーブポイントはシナリオ中途にあるため、クールタイム中にオートセーブが走りうる。
    ADR-0005 の「戦線離脱をセーブ対象に含めるか」と同じ性格の接合部
  - **どのシナリオで入手するかは未決**（ADR-0007）。決まるまで入手イベントは書かない。
    入手時期は入手前区間の猶予設計に波及するため、**P4 に入る前に主に確認すること**
- **受入**: S1→S4→G2冒頭まで、3ルートすべてで通る。プール下限5名を全経路で検証

### P5 — 研究システム

- 響／錠／灼 の配分UI、パーティ共有スキルとしての効果実装
- ステージ側の「突破線」オブジェクト（共振柱・可動機構・塩壁）
- 分岐2（S8）の判定（研究偏り＋直接選択の複合）
- **受入**: S11相当のテストステージで、3系統いずれでも突破できる

### P6 — 全12話の実装

データ投入が主作業になる。順序は **S5 → S7 → S8 → S9 → S10 → S11 → S12**。

- **前提: 固有名詞のかな置き換えが終わっていること**（ADR-0008。下記「P6 の前提」）
- プロップ層による時代差分（+28年、+55年）
- S4→S8、S1・S2→S9 のレイアウト再利用
- 代表20経路に**蘇生アイテム入手前／入手後**の違いが入る（ADR-0007）。
  入手前は操作キャラの猶予切れ＝シナリオ失敗がほぼ確定、入手後は AI 次第で復帰しうる
- **受入**: 代表20経路の自動プレイが全て最終話に到達

#### P6 の前提 — 固有名詞のかな置き換え（ADR-0008）

**ADR-0008（Accepted, 2026-09-14）により、画面に出る文字列に漢字は一切使えない。**
持つ字は かな全部＋数字＋記号 = **185タイル**（3バンク／予備7枚）、
**会話中に背景へ残るのは 71タイル**である。

したがって、企画書の固有名詞を**かなで書ける語に置き換える作業**が要る。
主の方針は「単純に読み仮名に直すだけでなく、**わかりやすく、短くて雰囲気のある語**への置き換え」である。

- 対象: シナリオ名15本／三勢力名3／研究3系統（響・錠・灼）／客将の二つ名6／
  G3 固有キャラ2（環守の影・環兵ゼロ号）／中心語（潮鳴り・環・機械兵・サラズ）／
  ルート名（静・動）／世代表記（画面に出るなら）
- 手順: **scenario-writer が案を出し、主が選ぶ。** spec-keeper が語を決めてはならない。
- 語が決まったら **別 ADR を起こして `docs/design-doc.md` を改訂する**（CLAUDE.md 第2条）。
- **完了期限: P6 のデータ投入より前。** シナリオ名は S1 から画面に出るため、
  `data/scenario.tsv` と `data/text/` への流し込みが始まった後では連鎖修正になる。
- 未決の付随論点（ADR-0008 帰結節の spec-keeper 所見）: **分かち書きの有無**
  （1行字数とウィンドウ行数設計に直結。text-budget / engine-dev に効く）、
  **同音衝突**（環／輪、潮／汐）、**短さと辞書圧縮効率は同じ方向を向かない**。

### P7 — テキストと予算の締め

- 辞書圧縮の本格投入、全台詞の流し込み
- グルド家のルート差分台詞（**ここだけ**）
- **かな表記の最終確認**（ADR-0008）。漢字混入をビルドで落とす検査が効いていること。
  置き換え語が全データで統一されていること（`data/scenario.tsv` の表示名と
  `data/text/` の台詞中の言及が食い違わないこと）
- PRG/CHR予算の最終調整。**フォント185タイル／背景71タイル**を `make budget` で検出できること
  （現行の `docs/budget.md` は CHRROM の総バイト数しか見ておらず、この制約を検出できない）
- **受入**: `make budget` が全項目で予算内

### P8 — 仕上げ

- ボス形態差分、エンディング分岐、タイトル・デモ
- 難易度調整、実機検証
- **受入**: 実機（またはPowerPak/EverDrive）で通しクリア

## 6. 並行作業の切り方

コンテキストの衝突を避けるため、同時に走らせるのは**最大2エージェント**まで。
安全に並行できる組み合わせ:

| 並行可 | 理由 |
|---|---|
| engine-dev × text-budget | 触るディレクトリが完全に分離 |
| stage-author × campaign-dev | データ形式が確定した後なら独立 |
| ai-dev × text-budget | 同上 |

**並行させてはいけない組み合わせ**: engine-dev × action-dev（当たり判定で衝突）、
stage-author × engine-dev（P3以前はローダ仕様が流動的）。

## 7. 最初に主が決めるべき3点

以下はエージェントに委ねず、人間が決めた方がよい。いずれもP1に入る前に確定させたい。

1. **セーブ方式** — バッテリーバックアップ（コスト増・快適）か、パスワード継続（安価・世代交代と相性が良い）か。世代ごとにパスワードを出す方式は、この企画の構造と実は噛み合う。
   - **決定（2026-09-12）: バッテリーバックアップ。加えてシナリオ中途の複数ポイントでオートセーブする。**
     オートセーブポイントは `data/scenario.tsv` で定義する（コードに話番号を書かない）。
     → [ADR-0001](decisions/0001-save-system.md)
2. **1画面の敵同時数** — スプライト欠けの許容ラインを決めないと、engine-devがAIの設計を固められない。
   - **決定（2026-09-12）: 敵同時6体、フリッカー許容（`MAX_ENEMIES = 6`）。**
     単純な巡回ではなく、操作キャラ・弾・至近の敵を優先する**重み付き巡回**を P2 で実験する。
     → [ADR-0002](decisions/0002-max-onscreen-enemies.md)
3. **操作キャラの切替可否** — ステージ中に切り替えられるか、出撃前に固定か。切替可にすると面白さは増すが、AI側の「操作されていない元操作キャラ」の扱いが増える。
   - **決定（2026-09-12）: 出撃前に固定。シナリオ中の交代は無し。**
     → [ADR-0003](decisions/0003-character-switching.md)

### 追加で決まったこと — キャラクターの死亡と失敗の扱い

上記3点に伴い、**企画書 §4 の「死亡は永続」を改める**方針変更が入った。
→ [ADR-0005](decisions/0005-death-and-failure.md)

- シナリオ中の戦闘で恒久的な死亡は起きない。HP が尽きた者は**ダウン（猶予中）**になる。
- 猶予切れ: 操作キャラ → **シナリオ失敗**（直前の**オートセーブポイント**から再開／中断）、
  AI キャラ → **戦線離脱**（そのシナリオ限り。恒久的な損失ではない）。
- 恒久的な死亡は**選択イベント起因のみ**。
- **猶予中（ダウン中）はキャラクターに関する操作が無効**。メタ操作（ゲームの中断）のみ可能。
  猶予中は先行入力を保持しない。→ [ADR-0006](decisions/0006-input-while-downed.md)（2026-09-12 決定）
- **蘇生手段はクールタイムつきのパーティ共有アイテム**。あるシナリオの通過で入手する。
  研究3系統（響／錠／灼）には手を付けない。クールタイムの長さはパラメータ（データ側）。
  → [ADR-0007](decisions/0007-revive-item.md)（2026-09-12 決定）
- ADR-0005 の未解決は**1件**に減った（**戦線離脱した AI キャラの縁値**）。
  該当箇所の実装（P4 の縁値・継承）に入る前に確認すること。
- ADR-0007 が新たに残した未決（**勝手に決めない**）:
  **どのシナリオで入手するか**／**クールタイムの具体値**／
  **AI キャラのダウン時にプレイヤーが手動で使えるか**（ポーズ仕様と同時に決める。ADR-0006 決定4）。
  入手時期は**入手前のシナリオで猶予が「眺めるだけの時間」のままになる**問題に直結するため、
  P4 に入る前に主に確認すること。
- **「どの AI 型が蘇生アイテムを使うか」は決定済み（2026-09-14）: どの型も使う。**
  ai-dev は P2 で **6型すべて**に蘇生行動を実装する。
  「どの型が使うか」の分岐をコードに書かず、**頻度・場面の差を `data/ai_params.tsv` の
  パラメータで表現できる形**にすること。**値は勝手に決めない。**
  → [ADR-0007 追補](decisions/0007-revive-item.md)

### 追加で決まったこと — テキストの文字種（2026-09-14）

**決定: 案A（かな全部）。漢字は使わない。** → [ADR-0008](decisions/0008-character-set.md)

- ひらがな80＋カタカナ80＋記号約15＋数字10 = **185タイル**。
  64タイル境界で **3バンク（192）／予備7枚**。**会話中に背景へ残るのは 71タイル。**
- **濁点は独立タイルにしない**（1字1タイル ＝ 1字1セル幅）。字数見積もりは素直な字数勘定でよい。
- **stage-author への影響が大きい。** 会話画面の背景が 71タイルに減った
  （起草時の想定132から大幅減）。会話画面の背景は「場所が分かる絵」ではなく記号的な枠として設計する。
- **会話ウィンドウ行の CHR バンク差し替え（MMC3 IRQ）の価値が上がった。**
  71タイルで成立しないと判明した場合の本命手段。**採否は主が決める**（engine-dev にはまだ降ろさない）。
- **漢字が使えないため、企画書の固有名詞をかなで書ける語に置き換える作業が発生する。**
  P6 のデータ投入より前に終わらせる（§5「P6 の前提」）。
